SECTION 1: COMPUTER SCIENCE FOUNDATIONS

1.1 Programming Fundamentals

Why it matters: Every professional mobile engineer must understand how programs execute, how memory is managed, and how to reason about code behavior before touching any framework.

1.1.1 Core Programming Concepts

  • Variables, Types, and Scope — stack vs heap allocation, value vs reference semantics. In Kotlin/Swift, understanding val/var and let/var is rooted in this.
  • Control Flow — loops, conditionals, early returns, guard clauses. Anti-pattern: deeply nested if-else trees (use early return / guard).
  • Functions and Closures — first-class functions, higher-order functions, closure capture lists, memory implications of closures capturing self (iOS retain cycles).
  • Error Handling — exceptions vs result types, panic vs recoverable errors, error propagation chains (Kotlin's Result<T>, Swift's throws/try/catch, Result<T, Error>).
  • Type Systems — static vs dynamic typing, strong vs weak typing, type inference, generics, covariance and contravariance.
  • Immutability — why immutable data leads to safer concurrent code and more predictable state management.
  • Null Safety — null pointer exceptions are among the top crash causes in mobile apps. Kotlin's null safety system and Swift's optionals exist to solve this.

1.1.2 Object-Oriented Programming (OOP)

  • Encapsulation — hiding implementation details, access modifiers (private, internal, public, protected). Mobile anti-pattern: exposing mutable state publicly.
  • Inheritance — subclassing, method overriding, fragile base class problem. Prefer composition over inheritance in modern mobile architectures.
  • Polymorphism — interfaces/protocols, dynamic dispatch vs static dispatch (performance implications in hot paths).
  • Abstraction — designing against interfaces, not implementations. Enables testability — the Repository pattern in Android/iOS is a direct application.
  • SOLID Principles:
  • Single Responsibility — each class does one thing (e.g., a UserRepository only handles data access, not business logic)
  • Open/Closed — open for extension, closed for modification (use interfaces)
  • Liskov Substitution — subtypes must be substitutable (critical for mock objects in tests)
  • Interface Segregation — don't force clients to depend on interfaces they don't use
  • Dependency Inversion — depend on abstractions, not concretions (the foundation of DI frameworks like Hilt, Koin, Swinject)

1.1.3 Functional Programming

  • Pure Functions — same input always produces same output, no side effects. Mobile benefit: predictable state transformations, easy unit testing.
  • Immutability — functional languages treat data as immutable. In mobile: data class in Kotlin with .copy(), struct in Swift.
  • Map, Filter, Reduce — fundamental list operations that replace verbose loops. Critical in Kotlin coroutines streams and Swift Combine.
  • Function Composition — chaining functions together. Foundation of reactive pipelines (RxJava, Combine, Flow).
  • Monads — Optional/Maybe, Result, Future/Promise. Understanding monads explains why flatMap exists and how async/await is conceptually a monad over futures.
  • Currying and Partial Application — less common in mobile but appears in functional Kotlin/Swift patterns.
  • Referential Transparency — expressions that can be replaced with their values. Enables memoization and caching optimizations.

Why it matters: Choosing wrong data structures causes performance bugs that are invisible until scale. A social feed that works with 50 items may freeze with 5,000.

1.2.2 Algorithm Complexity

  • Big O Notation — O(1), O(log n), O(n), O(n log n), O(n²). An O(n²) algorithm on a 10,000-item feed = 100 million operations, which will freeze the UI thread.
  • Space Complexity — memory usage analysis. Critical for mobile where RAM is constrained (2–8 GB typical).
  • Sorting Algorithms — QuickSort, MergeSort, TimSort. Know which your platform uses (Android: TimSort for stable sorts).
  • Search Algorithms — binary search on sorted data, DFS/BFS for tree traversal (navigation graphs, DOM trees).
  • Dynamic Programming — memoization patterns appear in caching layers, LRU cache implementations.
  • String Algorithms — tokenization, regex, fuzzy search (relevant for search UIs and NLP).

1.2.3 Algorithms Critical to Mobile

  • LRU Cache — Least Recently Used cache for image caching (Glide, Picasso, SDWebImage all implement this)
  • Diff Algorithms — DiffUtil in RecyclerView, React Native's virtual DOM reconciliation, Flutter's element diffing. Understanding diffing is critical for performant list updates.
  • Compression Algorithms — GZIP/Brotli for network requests, image compression (JPEG, WebP, HEIF)
  • Hashing — password hashing (bcrypt, Argon2), content hashing (SHA-256 for cache keys, checksums)

1.3 Concurrency and Parallelism

Why it matters: Mobile apps run on multi-core processors. Wrong concurrency = race conditions, deadlocks, ANR errors, app freezes.

1.3.1 Fundamental Concepts

  • Process vs Thread — OS processes have isolated memory spaces; threads share memory within a process.
  • Main/UI Thread — the single thread responsible for rendering in Android and iOS. Any blocking operation here causes dropped frames (< 16ms per frame for 60fps) or ANR (Application Not Responding).
  • Background Threads — for I/O, network calls, database access, computation.
  • Thread Pools — reusing threads to avoid expensive thread creation overhead (Android's Executors, iOS's DispatchQueue).
  • Race Conditions — two threads modifying shared state simultaneously. Causes non-deterministic bugs that are hard to reproduce.
  • Deadlocks — two threads waiting on each other, causing both to freeze. Common pattern: calling sync on the current queue in iOS GCD.
  • Starvation — lower-priority threads never get CPU time.
  • Atomic Operations — operations that complete in a single CPU instruction without interruption.

1.3.2 Synchronization Primitives

  • Mutex (Mutual Exclusion Lock) — only one thread enters a critical section at a time. High overhead.
  • Semaphore — counting-based access control. Limit concurrent network connections.
  • Read-Write Locks — multiple readers, exclusive writer. Better throughput than mutex for read-heavy caches.
  • Condition Variables — threads wait for conditions to be met.
  • Actor Model — Swift's actor keyword, Kotlin's Channel. Isolates state, serializes access.

1.3.3 Modern Concurrency Models

  • Coroutines (Kotlin) — lightweight cooperative concurrency. A single thread can run thousands of coroutines via suspension. suspend functions, launch, async/await, structured concurrency with CoroutineScope.
  • async/await (Swift) — Swift 5.5+ structured concurrency model. Task, TaskGroup, async let.
  • Reactive Programming — Kotlin Flow, Swift Combine, RxJava. Events as streams, operators to transform them.
  • Actors — Kotlin's experimental actor coroutine builder, Swift's actor type. State isolation without explicit locking.

1.4 Memory Management

Why it matters: Memory leaks are one of the top causes of mobile crashes and poor UX. iOS apps get terminated by the OS if memory pressure is too high.

1.4.1 Automatic Reference Counting (ARC) — iOS/Swift

  • Every object has a reference count. When count reaches 0, object is deallocated.
  • Retain Cycle — Object A holds strong reference to B, B holds strong reference to A. Neither is ever released. Common cause: closures capturing self strongly, delegate patterns.
  • Weak References — weak var doesn't increment retain count. Use for delegates and parent references.
  • Unowned References — like weak but assumed non-nil. Crashes if accessed after deallocation.
  • Memory Graph Debugger — Xcode tool to visualize retain cycles.

1.4.2 Garbage Collection — Android/JVM

  • JVM GC automatically reclaims unreachable objects. Advantage: no manual memory management. Disadvantage: GC pauses (stop-the-world events) can cause UI jank.
  • GC Generations — Young, Old, Permanent generations. Most objects die young (generational hypothesis).
  • Memory Leaks in Android — common causes: static references to Context, inner classes holding references to Activity, unregistered listeners/BroadcastReceivers, Handler leaks.
  • LeakCanary — automatic memory leak detection for Android.
  • Android Profiler — heap dump analysis, allocation tracking.

1.4.3 Memory Management Strategies

  • Object Pooling — reuse expensive objects instead of creating/destroying. RecyclerView implements this for ViewHolders.
  • Lazy Initialization — defer object creation until needed. Kotlin lazy { }, Swift lazy var.
  • Weak Data Structures — WeakHashMap in Java for caches that don't prevent GC.
  • Large Object Considerations — bitmaps/images are the largest memory consumers in mobile apps. Always downsample to display size, never load full-resolution unnecessarily.

1.5 Operating Systems Fundamentals

1.5.1 OS Concepts Relevant to Mobile

  • Process Scheduling — how the OS allocates CPU time. iOS uses priority-based scheduling; QoS (Quality of Service) classes dictate priority.
  • Memory Paging and Virtual Memory — OS swaps memory pages to storage. Mobile doesn't have traditional swap; instead, iOS kills background apps (jetsam/OOM killer).
  • File Systems — Android uses ext4/F2FS, iOS uses APFS. Understanding file system permissions, sandboxing.
  • App Sandboxing — iOS/Android apps run in isolated sandboxes. They can't read other apps' files. Implications for data sharing (Content Providers on Android, App Groups on iOS).
  • System Calls — apps request OS services via system calls (file I/O, network, camera). Understanding this explains why some operations require permissions.
  • IPC (Inter-Process Communication) — Android Intents, Binder IPC, iOS XPC for app extensions.

1.5.2 Android-Specific OS Concepts

  • Linux Kernel Basis — Android is built on Linux. Bionic libc (lighter than glibc), ART runtime.
  • Zygote Process — Android's process forking mechanism. Every app process is forked from Zygote, enabling fast startup.
  • Binder IPC — Android's primary IPC mechanism. AIDL (Android Interface Definition Language) for cross-process communication.
  • OOM Killer — Android kills processes based on a priority hierarchy: foreground > visible > service > background > empty. Understanding this is critical for proper service lifecycle management.

1.5.3 iOS-Specific OS Concepts

  • Darwin/XNU Kernel — iOS kernel combining Mach and BSD.
  • Process Jetsam — iOS's memory pressure mechanism. Apps can be terminated without warning. Always handle applicationDidReceiveMemoryWarning.
  • SpringBoard — iOS's home screen and app launcher process.
  • dyld — dynamic linker. Pre-warming and dyld cache optimizations affect app startup time.

1.6.1 Protocol Stack

Application Layer:  HTTP/HTTPS, WebSockets, gRPC, DNS
Transport Layer:    TCP (reliable), UDP (fast, unreliable)
Network Layer:      IP addressing, routing
Data Link Layer:    Ethernet, Wi-Fi, LTE/5G frames

1.6.2 TCP vs UDP

Feature TCP UDP
Reliability Guaranteed delivery No guarantee
Ordering In-order delivery Out-of-order
Overhead Higher (handshake) Lower
Use Case HTTP, APIs, file transfer Video streaming, gaming, DNS

Mobile implication: HTTP/HTTPS uses TCP. WebRTC (video calls) uses UDP. QUIC (HTTP/3) runs over UDP but adds reliability at the protocol level.

1.6.3 HTTP Protocol

  • HTTP/1.1 — persistent connections, chunked transfer, text-based headers. One request per connection (HOL blocking).
  • HTTP/2 — binary protocol, multiplexing (multiple requests over one connection), header compression (HPACK), server push. Significant performance improvement.
  • HTTP/3 / QUIC — runs over UDP. Eliminates TCP handshake latency. Handles network switching (WiFi to cellular) without dropping connections. Increasingly supported.
  • Request Methods — GET (idempotent, cacheable), POST (create), PUT (replace), PATCH (partial update), DELETE (remove), HEAD, OPTIONS.
  • Status Codes — 2xx success, 3xx redirect, 4xx client error, 5xx server error. Know: 200, 201, 204, 301, 302, 400, 401, 403, 404, 409, 422, 429, 500, 502, 503.
  • Headers — Authorization, Content-Type, Accept, Cache-Control, ETag, If-None-Match, X-Request-ID.
  • CORS — Cross-Origin Resource Sharing. Irrelevant for native mobile (no browser), but critical when building hybrid apps.

1.6.4 DNS

  • Domain resolution: domain name → IP address.
  • DNS Caching — TTL (Time To Live) on DNS records. Mobile apps can cache DNS resolutions to reduce latency.
  • DNS over HTTPS (DoH) — encrypts DNS queries, prevents ISP eavesdropping.
  • DNS Prefetching — resolve domain before user navigates to improve perceived speed.

1.7 Databases

1.7.1 Relational Databases (SQL)

  • ACID Properties:
  • Atomicity — transactions either fully complete or fully rollback
  • Consistency — database remains in valid state
  • Isolation — concurrent transactions behave as if serial
  • Durability — committed data survives failures
  • SQL Fundamentals — SELECT, JOIN (INNER, LEFT, RIGHT, FULL), GROUP BY, HAVING, subqueries, window functions, CTEs.
  • Indexing — B-tree indexes, composite indexes, covering indexes, index selectivity. Wrong indexing is the #1 cause of slow queries.
  • Transactions and Locking — optimistic vs pessimistic concurrency, deadlock prevention.
  • Common RDBMS — PostgreSQL (preferred for most backends), MySQL/MariaDB, SQLite (mobile local), SQL Server.

1.7.2 Non-Relational Databases (NoSQL)

  • Document Stores — MongoDB, Firestore. JSON-like documents. Good for flexible schemas, nested data (user profiles, content).
  • Key-Value Stores — Redis, DynamoDB. Blazing fast lookups. Good for sessions, caching, leaderboards.
  • Column-Family — Cassandra, HBase. Optimized for writes at massive scale. Good for time-series, activity feeds.
  • Graph Databases — Neo4j. Nodes and edges. Good for social graphs, recommendation engines.
  • Search Engines — Elasticsearch, OpenSearch. Full-text search, faceted filtering.

1.7.3 Database Selection Criteria

  • Structured + relational data + ACID required → PostgreSQL
  • Flexible schema + real-time sync + mobile first → Firestore
  • High-write throughput + time-series → Cassandra / InfluxDB
  • Caching + sessions → Redis
  • Full-text search → Elasticsearch

1.8 Distributed Systems Basics

1.8.1 CAP Theorem

Any distributed system can provide at most two of three guarantees: - Consistency — every read receives the most recent write - Availability — every request receives a response (not necessarily most recent) - Partition Tolerance — system operates despite network failures

Network partitions are inevitable, so you choose: CP (consistency + partition tolerance) or AP (availability + partition tolerance).

Mobile implications: When a user is offline (network partition), you must decide: show stale data (AP) or show nothing (CP). Most great mobile apps choose AP with eventual consistency and sync when online.

1.8.2 Eventual Consistency

  • Writes propagate asynchronously across nodes.
  • Reads may return stale data temporarily.
  • System converges to consistency over time.
  • Conflict Resolution — last-write-wins (timestamp-based), vector clocks, CRDTs (Conflict-free Replicated Data Types) — used in offline-first mobile apps (like Notion, Linear).

1.8.3 Service Communication Patterns

  • Synchronous — request/response (REST, gRPC). Caller waits for response. Simple but creates coupling.
  • Asynchronous — message queues (Kafka, RabbitMQ, SQS). Decouples producer and consumer. Better resilience.
  • Event-Driven — services emit events, interested services subscribe. Loose coupling, high scalability.

1.8.4 Scalability Patterns

  • Horizontal Scaling — add more instances (scale out). Stateless services make this easy.
  • Vertical Scaling — add more resources to one instance (scale up). Has limits.
  • Load Balancing — distribute traffic across instances. Round robin, least connections, IP hash.
  • Database Replication — primary writes, replica reads. Scales read-heavy workloads.
  • Sharding — split data across multiple databases. Each shard handles a subset of data (by user ID, geography).

1.9 System Design Fundamentals

1.9.1 The System Design Interview Framework (Also Production Reality)

  1. Clarify requirements — functional (what it does) vs non-functional (scale, latency, availability)
  2. Estimate scale — DAU, QPS, storage needs, bandwidth
  3. High-level design — components and their relationships
  4. Deep dive — critical components, data models, API design
  5. Identify bottlenecks — and mitigation strategies

1.9.2 Back-of-the-Envelope Estimation

  • 1 million DAU × 10 actions/day = 10M events/day = ~116 QPS
  • Read-heavy systems: 80/20 rule (80% reads, 20% writes)
  • 1 image at 1MB × 1M users uploading = 1TB/day storage
  • These estimates drive infrastructure decisions.

1.9.3 Common System Design Components

  • CDN — globally distributed edge servers for static assets and cached responses
  • Load Balancer — L4 (TCP) vs L7 (HTTP-aware). Nginx, AWS ALB, HAProxy.
  • API Gateway — single entry point for all clients. Rate limiting, auth, request routing, transformation.
  • Message Queue — async communication, buffering, decoupling. Kafka, SQS, RabbitMQ.
  • Cache — Redis/Memcached. Cache aside, read-through, write-through patterns.
  • Object Storage — S3 for files, images, videos. Not a file system but infinitely scalable.
  • Search — Elasticsearch for full-text, Algolia for instant search.

SECTION 2: MOBILE APPLICATION FUNDAMENTALS

2.1 Mobile App Lifecycle

2.1.1 Understanding App States

Mobile apps don't run like desktop apps. The OS can terminate them at any time, especially on iOS. Understanding lifecycle states is foundational.

Android States:

Created → Started → Resumed (FOREGROUND)
Resumed → Paused (another activity on top, partially visible)
Paused → Stopped (fully hidden/backgrounded)
Stopped → Destroyed (system kills for resources, or user closes)
Any State → Killed (OOM killer, low memory)

iOS States:

Not Running → Inactive (transition state) → Active (FOREGROUND)
Active → Background (user pressed home, incoming call)
Background → Suspended (OS freezes execution, but still in memory)
Suspended → Terminated (OS reclaims memory)

Critical lifecycle events to handle: - Save state before going background — users expect to return where they left off - Release resources on stop/background — camera, sensors, audio sessions - Restore state on resume — from persistent storage - Handle unexpected termination — crash or OOM kill should not corrupt data

2.1.2 Configuration Changes (Android-Specific)

When the device rotates, the Activity is destroyed and recreated. This is one of the most common sources of Android bugs.

Solutions: - ViewModel survives configuration changes - onSaveInstanceState() for small, transient state - rememberSaveable in Jetpack Compose - Retain Fragment (deprecated) — don't use

2.2 Mobile App Architecture Patterns

2.2.1 Why Architecture Matters in Mobile

  • Testability — untestable code = bugs you can't catch before shipping
  • Scalability — adding features without breaking existing ones
  • Maintainability — onboarding new team members, reducing cognitive load
  • Separation of Concerns — UI code mixed with business logic = spaghetti

2.2.2 Layered Architecture

┌─────────────────────────────────┐
│      Presentation Layer         │  ← UI Components, ViewModels
├─────────────────────────────────┤
│        Domain Layer             │  ← Use Cases, Business Logic
├─────────────────────────────────┤
│         Data Layer              │  ← Repositories, Data Sources
└─────────────────────────────────┘

Each layer only knows about the layer below it. The Domain layer is pure Kotlin/Swift — no Android/iOS imports. This makes it fully unit-testable.

2.2.3 MVC (Model-View-Controller)

  • Model — data and business logic
  • View — UI rendering
  • Controller — mediates between Model and View

Problem in mobile: Controller (Activity/ViewController) tends to grow enormous, violating SRP. Called "Massive View Controller" in iOS community.

2.2.4 MVP (Model-View-Presenter)

  • View — passive UI, delegates all logic to Presenter
  • Presenter — handles business logic, updates View via interface
  • Model — data

Benefit: View is easily mockable for testing. Problem: Presenter-View contract (interfaces) creates boilerplate.

2.2.5 MVVM (Model-View-ViewModel)

  • View — observes ViewModel for state changes
  • ViewModel — holds and exposes UI state, handles user actions
  • Model — data sources

The dominant pattern in modern Android (with LiveData/StateFlow) and iOS (with Combine/ObservableObject). ViewModel survives configuration changes.

2.2.6 MVI (Model-View-Intent)

  • Intent — user actions are modeled as discrete intents
  • State — single immutable state object
  • Side Effects — one-time events (navigation, toasts)

Benefit: completely unidirectional data flow, highly predictable, excellent for testing. Popular in Android with Orbit MVI, Decompose.

2.2.7 Clean Architecture

Extends layered architecture with strict dependency rules: - Dependencies only point inward - Domain/Use Cases have zero platform dependencies - Outer layers can know about inner, never the reverse

External (Frameworks, UI, DB, Network)
    ↓ depends on
Interface Adapters (ViewModels, Presenters, Gateways)
    ↓ depends on
Application Business Rules (Use Cases)
    ↓ depends on
Enterprise Business Rules (Entities)

2.3 Native vs Cross-Platform Development

2.3.1 Native Development

  • Android: Kotlin + Jetpack Compose / XML
  • iOS: Swift + SwiftUI / UIKit
  • Pros: Best performance, full API access, platform-native UX, first-party framework support
  • Cons: Two separate codebases, higher development cost, separate teams

2.3.2 Cross-Platform Options

Framework Language Rendering Performance
Flutter Dart Custom (Skia/Impeller) Near-native
React Native JavaScript/TypeScript Native components via bridge Good, improved with JSI
Kotlin Multiplatform Kotlin Native UI per platform Native
Xamarin/MAUI C# Native Good
Ionic/Capacitor Web tech WebView Lower

Flutter: Custom rendering engine means pixel-perfect consistency across platforms. Growing rapidly. Best for high-performance, visually consistent apps.

React Native: JavaScript bridge to native components. Largest ecosystem. New Architecture (JSI, Fabric, Turbo Modules) significantly improves performance.

Kotlin Multiplatform (KMP): Share business logic, networking, and data layers in Kotlin; native UI per platform. Best of both worlds philosophy. Adopted by companies like Netflix, Touchlab.

2.3.3 Decision Framework

  • Startup / MVP / Small team → Flutter or React Native
  • Complex, performance-critical UX → Native or Flutter
  • Large existing native codebase → KMP to share logic
  • Web-first team expanding to mobile → React Native or Capacitor
  • Enterprise with .NET → MAUI

2.4 Offline-First Architecture

Why it matters: Mobile networks are unreliable. Users on the subway, in elevators, in rural areas — they expect apps to work. Offline-first is a competitive differentiator.

2.4.1 Core Principles

  1. Local first — always read from and write to local database first
  2. Sync in background — network is an optimization, not a requirement
  3. Conflict resolution — handle concurrent edits on multiple devices
  4. Incremental sync — don't re-download everything, sync only changes

2.4.2 Offline Storage Options

  • Android: Room (SQLite), DataStore, Shared Preferences
  • iOS: Core Data, SQLite (via FMDB, GRDB), UserDefaults
  • Cross-platform: Realm, SQLDelight, Hive (Flutter)

2.4.3 Sync Strategies

  • Timestamp-based sync — sync all records changed after last sync timestamp. Simple but susceptible to clock drift.
  • Change-data capture (CDC) — backend tracks all changes in a log. Mobile consumes the log.
  • CRDTs (Conflict-free Replicated Data Types) — data structures that automatically merge concurrent edits without conflicts. Used by Notion, Figma, Automerge.
  • Operational Transformation — Google Docs approach for real-time collaborative editing.

2.4.4 Conflict Resolution Strategies

  • Last Write Wins (LWW) — server timestamp determines winner. Simple but lossy.
  • Merge — intelligently merge non-conflicting fields, flag conflicts for user resolution.
  • Version vectors — track causality of updates across devices.

2.5 State Management

Why it matters: State management is where most mobile app complexity lives. Getting it wrong causes stale UI, race conditions, and unpredictable behavior.

2.5.1 Types of State in Mobile Apps

  • UI State — what's currently visible (loading, error, content, empty)
  • User Data — profile, preferences, authentication status
  • Navigation State — current screen, backstack
  • Session State — ephemeral state that survives configuration changes but not process death
  • Persistent State — database, shared preferences, keychain

2.5.2 State Management Patterns

Unidirectional Data Flow (UDF):

User Action → Intent → State Reducer → New State → UI Update

One source of truth. State only changes through defined paths. Debugging is easy because state changes are traceable.

Reactive State: State is observable. UI automatically updates when state changes. Foundation of Compose, SwiftUI, Flutter.

Global State vs Local State: Don't over-engineer. A simple form's text field value doesn't need a global state manager. Push state as close to the leaf node as possible.

2.5.3 Android State Management

  • StateFlow / MutableStateFlow — Kotlin coroutines-based observable state
  • LiveData — lifecycle-aware observable. Being replaced by StateFlow in new code.
  • Compose remember / rememberSaveable — local Composable state
  • ViewModels — survives configuration changes, holds screen state

2.5.4 iOS State Management

  • @State — local view state in SwiftUI
  • @StateObject / @ObservedObject — ViewModel-like objects
  • @EnvironmentObject — dependency injection through view hierarchy
  • Combine — reactive streams for complex state
  • TCA (The Composable Architecture) — popular community architecture for SwiftUI

2.5.5 Flutter State Management

  • setState — simplest, local to Widget
  • Provider — recommended by Flutter team for simple cases
  • Riverpod — improved Provider with compile-time safety
  • Bloc/Cubit — BLoC (Business Logic Component) pattern, most scalable
  • GetX — all-in-one but opinionated

2.6 Navigation Systems

2.6.1 Navigation Fundamentals

  • Stack Navigation — push/pop model. Most common. Back button pops.
  • Tab Navigation — bottom tabs or top tabs. Multiple parallel stacks.
  • Drawer Navigation — hamburger menu.
  • Modal Navigation — sheets, dialogs presented over current content.

2.6.2 Deep Linking

Deep links allow external URLs to open specific screens inside the app.

Types: - URI Scheme Deep Links — myapp://product/123. Require app to be installed. Can be hijacked by malicious apps. - Android App Links — HTTPS-based deep links with domain verification. Verified, secure. - iOS Universal Links — HTTPS-based. Requires apple-app-site-association file on server. - Deferred Deep Links — user hasn't installed the app yet. Open App Store, install, then open the intended screen. Firebase Dynamic Links, Branch.io.

Implementation checklist: - Register URL schemes / associated domains - Handle incoming intents/userActivities - Parse URL parameters - Navigate to correct screen with parsed parameters - Handle edge cases: not logged in, content deleted

2.6.3 Android Navigation

  • Intent-based — start Activity with explicit or implicit intents. Old but still common.
  • Jetpack Navigation Component — single-Activity architecture with NavGraph. Safe args, deep link support, animation support.
  • Compose Navigation — NavHost and NavController. Type-safe routes with Kotlin serialization.

2.6.4 iOS Navigation

  • UINavigationController — imperative push/pop
  • UITabBarController — tab-based navigation
  • NavigationStack (SwiftUI) — declarative, path-based navigation. iOS 16+.
  • Coordinator Pattern — encapsulates navigation logic outside ViewControllers. Highly testable.

2.7 Device Hardware Integrations

2.7.1 Common Hardware APIs

  • Camera — photo capture, video recording, QR/barcode scanning (ML Kit, Vision framework)
  • Location / GPS — foreground vs background location permissions, geofencing, significant location changes (battery-efficient)
  • Accelerometer / Gyroscope — motion detection, step counting, screen rotation
  • Biometrics — fingerprint (Android BiometricPrompt), Face ID (iOS LocalAuthentication)
  • NFC — contactless payments (Apple Pay, Google Pay), tag reading
  • Bluetooth — BLE (Bluetooth Low Energy) for IoT devices, wearables
  • Microphone — speech recognition, audio recording
  • Vibration / Haptics — UIFeedbackGenerator (iOS), Vibrator API (Android)

2.7.2 Permission Management

Every hardware API requires explicit user permission. Best practices: - Request permissions contextually (when user performs an action needing the permission) - Never request all permissions on first launch - Provide rationale before requesting - Gracefully degrade if permission denied - Handle "never ask again" state (guide to settings)

2.7.3 Background Execution Constraints

Both platforms heavily restrict background execution to preserve battery: - Android: WorkManager for deferrable background work, Foreground Services for user-visible background work, JobScheduler for system-scheduled work - iOS: Background App Refresh (discretionary), Background fetch, Push notifications to wake app, Background processing tasks (BGTaskScheduler)

2.8 Mobile Performance Optimization

2.8.1 Rendering Performance

  • 60fps target — 16.67ms per frame budget
  • Android Janky frames — frame exceeds 16ms. Systrace, Android GPU Inspector, Compose performance tools.
  • iOS CADisplayLink — frame cadence tied to display refresh rate. Instruments → Core Animation.
  • Avoid doing on main thread: network calls, database queries, JSON parsing, image decoding, large computations.

2.8.2 List Performance

  • RecyclerView — ViewHolder pattern, view recycling. Critical: don't load full-resolution images in list cells.
  • Compose LazyColumn/LazyRow — composition recycling, key parameter for stable identity.
  • iOS UITableView/UICollectionView — dequeueReusableCell, prefetching delegate.
  • SwiftUI List — lazy loading by default.
  • Anti-patterns: inflate new views on scroll, block main thread during scroll, large complex item layouts.

2.8.3 Startup Time Optimization

  • Cold start — app process doesn't exist. Most expensive.
  • Warm start — process exists but Activity was destroyed.
  • Hot start — app returns from background. Cheapest.

Optimization strategies: - Defer non-critical initialization (analytics, ad SDKs) - Lazy load resources - App startup profiling (Android Baseline Profiles, iOS Instruments) - Reduce APK/IPA size (affects download time → first open)

2.8.4 Network Performance

  • Request batching — combine multiple API calls into one
  • Response compression — GZIP reduces payload by 70-80%
  • Image optimization — WebP (Android), HEIF (iOS), serve appropriate resolutions per device density
  • HTTP caching — Cache-Control, ETag headers
  • Connection pooling — reuse HTTP connections (OkHttp, URLSession)

        kSecValueData as String: password.data(using: .utf8)!,
        kSecAttrAccessible as String: kSecAttrAccessibleWhenUnlockedThisDeviceOnly
    ]
    SecItemDelete(query as CFDictionary) // Delete existing
    let status = SecItemAdd(query as CFDictionary, nil)
    guard status == errSecSuccess else { throw KeychainError.unhandledError(status) }
}

7.1 API Design

7.1.1 REST API Design Principles

REST (Representational State Transfer) is the dominant API paradigm for mobile backends.

Resource-based URLs:

GET    /users              → list users
POST   /users              → create user
GET    /users/{id}         → get user
PUT    /users/{id}         → replace user
PATCH  /users/{id}         → update user fields
DELETE /users/{id}         → delete user
GET    /users/{id}/posts   → user's posts (nested resource)

Best practices: - Use nouns, not verbs in URLs (/users not /getUsers) - Use plural resource names - Use HTTP methods semantically - Version your API: /v1/users or Accept: application/vnd.api.v1+json - Return consistent error responses:

{
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "User with id '123' not found",
    "details": {},
    "request_id": "req_abc123"
  }
}
  • Use HTTP status codes correctly
  • Implement pagination for collections: cursor-based (preferred for mobile) vs offset-based
  • Use ETags for conditional requests (avoid re-downloading unchanged data)
  • HATEOAS for discoverability (rarely implemented fully in practice)

7.1.2 API Versioning Strategies

Strategy Example Pros Cons
URL path /v1/users Explicit, cacheable URL changes per version
Header Accept: application/vnd.api.v1+json Clean URLs Less visible
Query param /users?version=1 Simple Mixes params with resources

Mobile apps are slow to update. Never break existing API contracts. Add fields (additive), never remove. Maintain old versions for 6-12 months after deprecation.

7.3 Authentication Systems

7.3.1 JWT (JSON Web Tokens)

Header.Payload.Signature
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMiLCJleHAiOjE2MzUwMDAwMDB9.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Header: Algorithm + type Payload: Claims (sub, exp, iat, custom claims). Not encrypted — only signed. Never put secrets. Signature: HMAC-SHA256 or RSA signature to verify authenticity.

Access + Refresh token pattern: - Access token: short-lived (15 minutes). Sent with every request. Stateless. - Refresh token: long-lived (30 days). Stored securely (Keychain/Keystore). Used only to get new access token. - Refresh rotation: issue new refresh token with each use. Old tokens invalidated. Prevents replay attacks.

Client → POST /auth/login → Server
Server → { accessToken, refreshToken } → Client
Client → GET /api/data [Authorization: Bearer {accessToken}] → Server
Server → 401 Unauthorized → Client (access token expired)
Client → POST /auth/refresh { refreshToken } → Server
Server → { newAccessToken, newRefreshToken } → Client

7.3.2 OAuth 2.0 for Mobile (PKCE Flow)

Mobile apps are "public clients" — they can't store a client secret securely. PKCE (Proof Key for Code Exchange) solves this.

1. Generate code_verifier (random 32-byte string)
2. code_challenge = base64url(sha256(code_verifier))
3. Redirect to Authorization URL with code_challenge
4. User authenticates on authorization server (Google, Apple, etc.)
5. Authorization server returns code to app (via deep link)
6. Exchange code + code_verifier for tokens
   → Server verifies sha256(code_verifier) == code_challenge
   → Prevents code interception attacks

Libraries: AppAuth (Android/iOS), universal standard.

7.3.3 Sign in with Apple (Required for iOS)

Apple mandates Sign in with Apple if any other third-party social login (Google, Facebook) is offered.

7.4 Microservices Architecture

7.4.1 Microservices vs Monolith

Monolith advantages: - Simple to develop, test, deploy initially - No network latency between components - Easy transactions (everything in one DB) - Best for: startups, small teams, early-stage products

Microservices advantages: - Independent scaling (scale only notification service, not entire app) - Technology flexibility per service - Fault isolation (one service failing doesn't take down everything) - Independent deployments (teams can release without coordinating) - Best for: large teams, proven product, high scale

Anti-pattern: Distributed monolith — microservices that are tightly coupled and must always deploy together. Worst of both worlds.

7.4.2 Microservice Communication

  • Synchronous (REST/gRPC) — service A calls service B, waits for response. Simple but creates coupling.
  • Asynchronous (Message Queue) — service A publishes event, service B consumes when ready. Decoupled but complex.
  • Service Mesh — infrastructure layer (Istio, Linkerd) for service-to-service communication: mTLS, circuit breaking, retry, tracing.

7.4.3 Event-Driven Architecture

User Service → UserRegistered event → Message Broker (Kafka) 
    ↓ consumed by
Email Service → sends welcome email
Notification Service → creates push preferences
Analytics Service → records new user
Referral Service → processes referral code

Benefits: Services are completely decoupled. Adding a new service doesn't require changing the emitter. Highly scalable.

Event Schema Design: Use a schema registry (Confluent Schema Registry) with Avro or Protobuf. Prevents breaking consumers when schema evolves.

7.6.2 Cache Strategies

  • Cache Aside (Lazy Loading) — check cache, if miss → load from DB → write to cache → return. Most common. Possible cache miss on first read.
  • Read-Through — cache is in front of DB. Cache handles DB reads automatically.
  • Write-Through — write to cache and DB simultaneously. No stale data but added write latency.
  • Write-Behind (Write-Back) — write to cache, async write to DB. Fast writes, risk of data loss.

SECTION 8: DATABASE ENGINEERING

8.1 SQL Database Design

8.1.1 Data Modeling Principles

  • Normalization — eliminate redundancy. 1NF, 2NF, 3NF, BCNF. Normalized = consistent, less storage. Denormalized = faster reads.
  • Entity-Relationship Diagrams — model entities and their relationships before writing schemas.
  • One-to-Many — user has many posts. Foreign key on many side.
  • Many-to-Many — users follow users. Junction/bridge table.
  • One-to-One — user has one profile. Foreign key with UNIQUE constraint.

8.1.2 PostgreSQL for Mobile Backends

CREATE TABLE users (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    username    VARCHAR(50) UNIQUE NOT NULL,
    email       VARCHAR(255) UNIQUE NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE posts (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    content     TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()

-- Indexes
CREATE INDEX idx_posts_user_id ON posts(user_id);
CREATE INDEX idx_posts_created_at ON posts(created_at DESC); -- For feed queries

-- Composite index for common query: user's recent posts

-- Partial index for active users only
CREATE INDEX idx_active_users ON users(email) WHERE deleted_at IS NULL;

8.1.3 Query Optimization

-- Bad: N+1 queries
SELECT * FROM users; -- 100 users
-- Then for each user:
SELECT * FROM posts WHERE user_id = ?; -- 100 queries!

-- Good: JOIN
SELECT u.*, p.* FROM users u
LEFT JOIN posts p ON p.user_id = u.id
WHERE u.id = ANY($1::uuid[]);

-- EXPLAIN ANALYZE to understand query plan
EXPLAIN ANALYZE SELECT * FROM posts WHERE user_id = $1 ORDER BY created_at DESC LIMIT 20;
-- Look for: Seq Scan (bad for large tables) vs Index Scan (good)

8.1.4 Connection Pooling

Database connections are expensive. Mobile backends with many instances need connection pooling. - PgBouncer — PostgreSQL connection pooler. Sits between app and DB, maintains a pool of actual DB connections. - Transaction-mode pooling — connection returned to pool after each transaction. Most efficient. - Rule of thumb: PostgreSQL handles ~100-200 concurrent connections. PgBouncer can handle thousands.

8.3 Database Replication and Sharding

8.3.1 Replication

  • Primary-Replica (Master-Slave) — primary handles all writes, replicas serve reads.
  • Synchronous replication — write confirmed only after replica acknowledges. Slower writes, no data loss.
  • Asynchronous replication — write confirmed after primary writes. Fast, potential data loss if primary fails.
  • Read replicas — add as many as needed. Route read-heavy queries (analytics, reports) to replicas.

Mobile implications: Most mobile backends are read-heavy. 5-10x read replicas is common.

8.3.2 Sharding

Split data horizontally across multiple database instances.

Sharding strategies: - Range-based — shard by ID range. Risk of hotspots. - Hash-based — shard = hash(user_id) % num_shards. Even distribution. - Geographic — shard by user region. Data sovereignty compliance, lower latency. - Directory-based — lookup service maps entity to shard. Flexible but adds hop.

Challenges: Cross-shard transactions (avoid or use saga pattern), re-sharding (pre-shard with 1000+ logical shards), cross-shard queries.

8.4.3 Sync Engine Design

class SyncEngine(
    private val api: ApiService,
    private val db: AppDatabase
) {
    suspend fun sync() {
        val lastSyncTime = db.metaDao().getLastSyncTime()

        // Fetch changes from server
        val serverChanges = api.getChangesSince(lastSyncTime)

        db.withTransaction {
            // Apply server changes to local DB
            serverChanges.upserts.forEach { db.postDao().upsert(it.toEntity()) }
            serverChanges.deletes.forEach { db.postDao().delete(it.id) }

            // Push local changes to server
            val localPendingChanges = db.postDao().getPendingSync()
            val syncResult = api.pushChanges(localPendingChanges)

            // Mark local changes as synced
            db.postDao().markSynced(syncResult.acknowledgedIds)

            // Update sync timestamp
            db.metaDao().setLastSyncTime(serverChanges.serverTimestamp)
        }
    }
}

SECTION 9: AUTHENTICATION & SECURITY

9.1 Security Architecture

9.1.1 Defense in Depth

Security is layered. If one layer fails, others contain the breach.

Layer 1: Network (TLS, certificate pinning, WAF)
Layer 2: API Gateway (rate limiting, DDoS protection, authentication)
Layer 3: Application (input validation, authorization, business logic security)
Layer 4: Data (encryption at rest, field-level encryption, access controls)
Layer 5: Infrastructure (VPC, firewalls, IAM, secret management)

9.1.2 OWASP Mobile Top 10 (2024)

  1. M1: Improper Credential Usage — hardcoded credentials, weak passwords, credentials in logs. Fix: use secrets management, proper key storage.
  2. M2: Inadequate Supply Chain Security — vulnerable third-party libraries, unsigned builds. Fix: dependency scanning (OWASP Dependency Check), binary signing.
  3. M3: Insecure Authentication/Authorization — broken auth flows, missing server-side auth. Fix: proper OAuth/JWT, always validate server-side.
  4. M4: Insufficient Input/Output Validation — SQL injection, XSS (in WebViews), path traversal. Fix: parameterized queries, input sanitization.
  5. M5: Insecure Communication — HTTP usage, no certificate validation, custom crypto. Fix: HTTPS everywhere, certificate pinning, standard crypto libraries.
  6. M6: Inadequate Privacy Controls — collecting unnecessary data, storing PII in logs. Fix: data minimization, GDPR compliance.
  7. M7: Insufficient Binary Protections — decompilable code, debug flags in release, emulator detection bypass. Fix: R8/ProGuard, release builds, Play Integrity.
  8. M8: Security Misconfiguration — overly permissive app permissions, exported components. Fix: minimum permissions, unexport components not needed externally.
  9. M9: Insecure Data Storage — cleartext SQLite, world-readable files, sensitive data in screenshots. Fix: EncryptedSharedPreferences, Keychain, FLAG_SECURE.
  10. M10: Insufficient Cryptography — weak algorithms (MD5, SHA1, DES), hardcoded keys, ECB mode. Fix: AES-256-GCM, RSA-2048, Argon2 for passwords.

9.2 Encryption

9.2.1 Symmetric Encryption

Same key for encryption and decryption.

  • AES-256-GCM — gold standard for data encryption. Authenticated encryption (detects tampering). Use for: encrypting files, local database, network payload additional encryption.
  • ChaCha20-Poly1305 — alternative to AES, faster on devices without AES hardware acceleration.
// Android AES-GCM encryption
fun encrypt(data: ByteArray, keyAlias: String): EncryptedData {
    val keyGenerator = KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
    keyGenerator.init(
        KeyGenParameterSpec.Builder(keyAlias, KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
            .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
            .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
            .build()
    )
    val secretKey = keyGenerator.generateKey()

    val cipher = Cipher.getInstance("AES/GCM/NoPadding")
    cipher.init(Cipher.ENCRYPT_MODE, secretKey)

    return EncryptedData(cipher.doFinal(data), cipher.iv)
}

9.2.2 Asymmetric Encryption

Public key encrypts, private key decrypts. Used for key exchange, digital signatures.

  • RSA-OAEP — encrypt small data (session keys). RSA is slow for large data.
  • ECDSA — elliptic curve digital signatures. Smaller keys, faster than RSA.
  • ECDH — key exchange protocol. Derive shared secret from two key pairs (TLS).

9.2.3 Password Hashing

Never store passwords. Store hash of password with salt.

  • Argon2id — winner of Password Hashing Competition. Current best practice.
  • bcrypt — widely used, battle-tested. Still acceptable.
  • PBKDF2-HMAC-SHA256 — FIPS-approved, required in some compliance contexts.
  • Never use: MD5, SHA1, SHA256 without key derivation (too fast, susceptible to brute force).

9.3 SSL/TLS and Certificate Pinning

9.3.1 TLS Handshake

Client → ClientHello (TLS version, cipher suites) → Server
Client ← ServerHello (chosen cipher suite, certificate) ← Server
Client validates server certificate
Client → Key exchange material → Server
Both derive session keys
Client → Finished (encrypted) → Server
Client ← Finished (encrypted) ← Server
Secure channel established

9.3.2 Certificate Pinning

Pin your server's public key (preferred) or certificate to prevent MITM attacks even if a root CA is compromised.

// Android OkHttp certificate pinning

// iOS URLSession certificate pinning
class PinnedURLSessionDelegate: NSObject, URLSessionDelegate {
    func urlSession(_ session: URLSession, 
                    didReceive challenge: URLAuthenticationChallenge,
                    completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void) {
        guard let serverTrust = challenge.protectionSpace.serverTrust,
              let certificate = SecTrustGetCertificateAtIndex(serverTrust, 0) else {
            completionHandler(.cancelAuthenticationChallenge, nil)
            return
        }

        let serverCertData = SecCertificateCopyData(certificate) as Data
        let pinnedCertData = loadPinnedCertificate()

        if serverCertData == pinnedCertData {
            completionHandler(.useCredential, URLCredential(trust: serverTrust))
        } else {
            completionHandler(.cancelAuthenticationChallenge, nil)
        }
    }
}

Certificate pinning pitfalls: - Breaking changes when certificate rotates — always pin multiple keys (current + backup) - Apps can't connect without update if pin expires — use public key pinning (key persists across cert renewal) - Doesn't prevent all attacks (device with malicious root CA installed, rooted device)

10.5.4 Alerting Strategy

  • Symptom-based alerting — alert on user-impacting symptoms (high error rate, slow responses), not causes.

  • Alert fatigue — too many alerts = ignored alerts. Keep alert count small, high signal-to-noise ratio.

class NetworkClient {
    private let session: URLSession
    private let decoder = JSONDecoder()

    func request<T: Decodable>(_ endpoint: Endpoint) async throws -> T {
        var request = URLRequest(url: endpoint.url)
        request.httpMethod = endpoint.method.rawValue
        request.allHTTPHeaderFields = buildHeaders()

        if let body = endpoint.body {
            request.httpBody = try JSONEncoder().encode(body)
            request.setValue("application/json", forHTTPHeaderField: "Content-Type")
        }

        let (data, response) = try await session.data(for: request)

        guard let httpResponse = response as? HTTPURLResponse else {
            throw NetworkError.invalidResponse
        }

        guard 200..<300 ~= httpResponse.statusCode else {
            let error = try? decoder.decode(APIError.self, from: data)
            throw NetworkError.httpError(httpResponse.statusCode, error)
        }

        return try decoder.decode(T.self, from: data)
    }
}

12.2 Retry and Resilience

12.2.1 Exponential Backoff with Jitter

suspend fun <T> withRetry(
    maxAttempts: Int = 3,
    initialDelay: Long = 1000L,
    maxDelay: Long = 60_000L,
    factor: Double = 2.0,
    block: suspend () -> T
): T {
    var currentDelay = initialDelay
    repeat(maxAttempts - 1) { attempt ->
        try {
            return block()
        } catch (e: IOException) {
            if (attempt == maxAttempts - 2) throw e
        }
        val jitter = (Math.random() * currentDelay * 0.2).toLong()
        delay(currentDelay + jitter)
        currentDelay = (currentDelay * factor).toLong().coerceAtMost(maxDelay)
    }
    return block() // Last attempt
}

12.2.2 Circuit Breaker Pattern

class CircuitBreaker(
    private val failureThreshold: Int = 5,
    private val successThreshold: Int = 2,
    private val timeout: Long = 30_000L
) {
    private var state = State.CLOSED
    private var failureCount = 0
    private var lastFailureTime = 0L

    suspend fun <T> call(block: suspend () -> T): T {
        when (state) {
            State.OPEN -> {
                if (System.currentTimeMillis() - lastFailureTime > timeout) {
                    state = State.HALF_OPEN
                } else throw CircuitBreakerOpenException()
            }
            else -> Unit
        }

        return try {
            val result = block()
            onSuccess()
            result
        } catch (e: Exception) {
            onFailure()
            throw e
        }
    }

    private fun onSuccess() {
        if (state == State.HALF_OPEN) state = State.CLOSED
        failureCount = 0
    }

    private fun onFailure() {
        failureCount++
        lastFailureTime = System.currentTimeMillis()
        if (failureCount >= failureThreshold) state = State.OPEN
    }

    enum class State { CLOSED, OPEN, HALF_OPEN }
}

13.2 Feed Systems (Activity Streams)

13.2.1 Fan-out Architectures

Fan-out on write (Push model): - When user A posts, immediately write to all followers' feeds - Read is O(1) - Write is O(n) where n = number of followers - Problem: celebrities with millions of followers cause massive write amplification

Fan-out on read (Pull model): - When user opens feed, query and merge posts from all followed users - Read is O(n) where n = following count - Write is O(1) - Problem: slow reads for users following many people

Hybrid approach (Twitter/Instagram approach): - Use push for regular users (< 1M followers) - Use pull for celebrities (> 1M followers) - Merge on read: pre-computed feed + fresh celebrity posts

  • Statistical significance — p-value < 0.05 (95% confidence). Not "practically significant."
  • Multiple testing problem — running many tests increases false positive rate. Use Bonferroni correction.
  • Novelty effect — users engage more with new features simply because they're new. Run tests for full weekly cycles.
  • Guardrail metrics — ensure A/B test doesn't negatively impact other important metrics.

│  │  • All reads from local DB (SQLite/Room/CoreData)│  │
│  │  • All writes to local DB + sync queue          │  │
│  │  • Sync engine runs in background               │  │
│  └─────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────┘
                          ↕ (when online)
┌───────────────────────────────────────────────────────┐
│                   Sync Service                        │
│  • Incremental sync (timestamp/cursor based)          │
│  • Conflict resolution (server wins, LWW, or CRDT)   │
│  • Delta compression (only changed fields)            │
└───────────────────────────────────────────────────────┘

Sync Protocol:
1. Client sends: {last_sync_timestamp, pending_operations[]}
2. Server applies pending operations (with conflict detection)
3. Server returns: {server_operations_since[], new_cursor, conflicts[]}
4. Client applies server operations
5. Client resolves conflicts
6. Client updates sync cursor

CRDT-based approach (no conflicts):
• Counter: increment-only operation
• Set: add-only or remove-wins
• LWW-Register: last write wins by timestamp
• OR-Set (Observed-Remove Set): handles concurrent add/remove

18.2 CQRS and Event Sourcing

18.2.1 CQRS (Command Query Responsibility Segregation)

Separate read model from write model. Optimize each independently.

Commands (writes):          Queries (reads):
CreateOrder                 GetOrderById
UpdateOrderStatus           GetOrdersByUser
CancelOrder                 GetOrderHistory (analytics)
    ↓                            ↓
Write DB (normalized,       Read DB (denormalized,
ACID, PostgreSQL)           optimized, Elasticsearch/Redis)

Mobile applications benefit: the write path can be async (optimistic UI), read path returns pre-aggregated data (no N+1 queries).

18.2.2 Event Sourcing

Instead of storing current state, store sequence of events.

Events stored:
UserCreated { id, email, name, timestamp }
UserEmailChanged { id, newEmail, timestamp }
UserSubscribed { id, plan, timestamp }
UserUnsubscribed { id, reason, timestamp }

Current state = replay all events

Benefits: - Complete audit log - Time travel (what was the state on date X?) - Event replay (reprocess events with new business logic) - Decoupled event-driven systems

Drawbacks: - Query complexity (must replay events to get state — use snapshots) - Schema evolution (old events must be interpretable) - Higher storage usage

18.3 Domain-Driven Design (DDD)

18.3.1 Key DDD Concepts Applied to Mobile

  • Bounded Contexts — clear boundaries between domains. User module, Payment module, Notification module are separate bounded contexts with their own models.
  • Aggregates — cluster of domain objects treated as a unit. Order aggregate contains OrderLines, ShippingAddress. Load and save the whole aggregate.
  • Value Objects — immutable objects defined by their value, not identity. Email, Money, Address.
  • Domain Events — OrderPlaced, PaymentFailed, UserRegistered. Published when state changes.
  • Repositories — collection-like interface for aggregate retrieval and persistence.

// Bitmap loading with appropriate size
fun loadBitmap(context: Context, uri: Uri, targetWidth: Int, targetHeight: Int): Bitmap? {
    val options = BitmapFactory.Options().apply { inJustDecodeBounds = true }
    BitmapFactory.decodeStream(context.contentResolver.openInputStream(uri), null, options)

    // Calculate inSampleSize
    var sampleSize = 1
    while (options.outWidth / sampleSize > targetWidth * 2 ||
           options.outHeight / sampleSize > targetHeight * 2) {
        sampleSize *= 2
    }

    return BitmapFactory.Options().apply {
        inSampleSize = sampleSize
        inPreferredConfig = Bitmap.Config.RGB_565  // 2 bytes/pixel vs ARGB_8888's 4 bytes
    }.let { opts -> BitmapFactory.decodeStream(context.contentResolver.openInputStream(uri), null, opts) }
}

19.3 Battery Optimization

19.3.1 Battery Drain Causes

  • GPS usage — most power-hungry sensor. Request only needed accuracy, use significant location changes for coarse tracking.

22.1.2 Monetization Models

Freemium: - Free tier with limited features, paid tier for full access - Conversion rates typically 2-5% - Requires strong free value proposition (low enough friction) + clear premium upgrade path - Examples: Spotify, Slack, Dropbox

            let model = try! Entity.loadModel(named: "coffee_cup")
            anchor.addChild(model)
            arView.scene.anchors.append(anchor)
        }
    }
}

24.4 Zero-Trust Architecture

Traditional security: "Trust but verify inside the perimeter." Zero-trust: "Never trust, always verify."

Principles: - Verify every request regardless of location (inside or outside network) - Least-privilege access (minimum permissions for each service) - Microsegmentation (services can't freely communicate, explicit allowlisting) - Continuous monitoring and validation

Mobile implications: - Devices are endpoints that can't be fully trusted (jailbroken, compromised) - Certificate-based device authentication - App Attest / Play Integrity for device verification - Short-lived tokens, frequent re-authentication for sensitive operations

24.5 Privacy-First Engineering

24.5.1 Privacy by Design Principles

  1. Proactive, not reactive — build privacy in from the start
  2. Privacy as the default — users shouldn't have to opt-in to be protected
  3. Privacy embedded — not a bolt-on, not "privacy theater"
  4. Full functionality — privacy shouldn't sacrifice functionality
  5. End-to-end security — data protected throughout lifecycle
  6. Visibility and transparency — open about what is collected
  7. Respect for user privacy — user-centric design

24.5.2 Differential Privacy

Add mathematical noise to aggregate data to protect individual privacy while enabling statistical analysis. Used by: Apple (keyboard analytics), Google (Chrome privacy features), iOS Health app.

25.1 Recommended Stack Combinations

Startup / Small team (move fast): - Mobile: Flutter (single codebase) OR React Native - Backend: Firebase (Firestore + Auth + Functions) OR Supabase - CI/CD: GitHub Actions + Fastlane - Monitoring: Firebase Crashlytics + Analytics - Deployment: Vercel/Railway/Render for backend

25.2 Common Enterprise Best Practices

Code Quality: - Strict lint rules enforced in CI (zero tolerance for warnings in production code) - Mandatory code reviews (2 approvals for sensitive code — auth, payments) - Test coverage > 80% for domain layer - Dependency scanning (Snyk, OWASP Dependency Check)

Architecture: - ADRs for every significant decision - Clean Architecture with strict layer separation - Repository pattern consistently applied - No business logic in UI layer

Operations: - SLOs defined for all critical APIs - Runbooks for every alert - Blameless post-mortems - Staged rollouts for all releases

Security: - Regular penetration testing - SAST (Static Application Security Testing) in CI - DAST (Dynamic Application Security Testing) in staging - Secret rotation on schedule - Annual security training for all engineers

Process: - Quarterly technical roadmap reviews - Bi-annual architecture reviews - Weekly dependency updates - Monthly tech debt sprint

25.3 Core Mindset for Senior Engineers

  1. Think in systems — every decision has second-order effects. Ask: "What could go wrong at 10x scale? 100x?"

  2. Bias for simplicity — the best code is the code that doesn't need to be written. The best architecture is the simplest one that meets requirements.

  3. Optimize for change — code will be read and modified many more times than it's written. Write for the next developer.

  4. Security is not optional — security vulnerabilities are product bugs. Every feature should be reviewed for security implications.

  5. Measure everything — you can't improve what you don't measure. Instrument before optimizing.

  6. Users are real people — performance, accessibility, offline support — these make real differences in real people's lives.

  7. Own production — "it works on my machine" is not enough. Own the deployment, monitoring, and alerting for your code.

  8. Continuous learning — mobile and backend ecosystems evolve rapidly. Follow engineering blogs (Android Developers, Swift Evolution, AWS Architecture Blog), contribute to open source, attend conferences.
