1. Executive Summary

1.1 Vision

Veda is an AI-native, multi-stakeholder learning operating system built to make personalized, mastery-based education accessible from a primary school in rural Nepal to an enterprise reskilling program in Berlin — on the same platform, with the same underlying intelligence layer.

1.2 Mission

Eliminate the three structural failures of mainstream edtech:

  1. One-size content that ignores learner state, pace, and language.
  2. Disconnected stacks — LMS, assessment, analytics, communication living in separate silos.
  3. Outcome blindness — platforms that measure logins instead of learning.

Veda unifies content, pedagogy, assessment, and intelligence into a single graph-backed system whose core unit is the learner's evolving knowledge state, not the course.

1.3 Core Value Proposition

Stakeholder What Veda Delivers
Students Adaptive, multilingual learning paths with an always-available AI tutor grounded in their curriculum.
Teachers Automated grading, plagiarism/AI-content detection, classroom analytics, and lesson-plan co-authoring.
Institutions A single multi-tenant platform replacing 4–6 vendors (LMS, proctoring, analytics, comms, content).
Parents Transparent, jargon-free progress with concrete next-step suggestions.
Governments Population-level learning analytics, equity dashboards, and curriculum alignment tooling.
Enterprises Skill-graph-based reskilling with measurable proficiency rather than completion certificates.
Researchers Anonymized, consented learning datasets and an experimentation API.

1.4 Unique Competitive Advantages

  1. Knowledge-graph-first architecture. Every concept, prerequisite, and assessment item is a node — enabling true mastery tracking instead of percentage-based grading.
  2. Composable AI tutor that uses RAG over the institution's own curriculum, not generic web data.
  3. Offline-first mobile core. Critical for emerging markets where most growth in edtech demand exists.
  4. Multi-tenant by design — same code path serves a single school, a state government, and an enterprise L&D org.
  5. Open data exports & LTI 1.3 compliance — escape velocity from vendor lock-in becomes a marketing asset.

1.5 Target Audience (Tiered)

  • Tier 1 (Wedge): Mid-sized K-12 schools and universities in South Asia, Southeast Asia, and Africa — currently underserved by Canvas/Blackboard, overserved by Google Classroom (which lacks pedagogy depth).
  • Tier 2 (Expansion): Test-prep & vocational training institutes; corporate L&D for SMBs.
  • Tier 3 (Strategic): Government education ministries; large enterprise reskilling.

1.6 Key Business Opportunities

Fact The global edtech market is large and fragmented; mature players dominate Western higher-ed but emerging-market K-12 and enterprise upskilling remain structurally underserved. Assumption Specific TAM/SAM figures vary widely between analyst firms; we therefore frame opportunity in terms of wedge, beachhead, and expansion rather than a fabricated TAM number.

1.7 Long-Term Scalability Potential

Because the core data structure is a knowledge graph, Veda can extend horizontally into adjacent verticals — medical CME, legal CLE, professional certifications — without re-architecting. The same recommendation engine that suggests the next algebra concept can suggest the next surgical technique module.

3. Complete Technology Stack

3.1 Programming Languages — Selection Matrix

Language Where Used Why Chosen Tradeoffs
TypeScript Frontend (web, mobile-RN, Node services) Strong types catch entire bug classes; massive ecosystem; full-stack reuse. Build complexity; runtime is still JS.
Python AI/ML, data pipelines, internal tooling Default lingua franca of ML; richest library ecosystem. GIL limits CPU concurrency; slower than Go/Rust for hot paths.
Go High-throughput services (API gateway, real-time, ingestion) Predictable latency, low memory, simple deploy, great concurrency primitives. Verbose error handling; less expressive than Rust for complex types.
Rust Performance-critical components (assessment proctoring agent, video transcode orchestration) Memory safety + C-class speed; ideal where reliability is non-negotiable. Steep learning curve; slower iteration.

Swift iOS native modules Required for high-quality iOS UX, ARKit integration. Apple-ecosystem lock-in.

Recommendation Recommendation: TypeScript + Python + Go is the 80/20 stack. Reach for Rust only when profiling proves it. Reach for Kotlin/Swift only for native modules wrapping React Native or Flutter.

This is three runtimes — the discipline limit. More than three becomes operational debt.

Educational Personalization Algorithm — composite design

mastery_score(student, concept) =
    0.4 × BKT_posterior(student, concept)          # probabilistic mastery
  + 0.3 × IRT_ability_estimate(student, item_bank) # item response theory
  + 0.2 × spaced_repetition_recall(student, concept)
  + 0.1 × engagement_proxy(student, concept)

next_recommendation =
    argmax over candidate_concepts of
        learning_gain(student, concept)
        − cognitive_load(student, current_session)
    subject to: prerequisites_met(student, concept)

Fact BKT (Bayesian Knowledge Tracing), IRT (Item Response Theory), and spaced repetition are well-established, peer-reviewed pedagogy. Their composition is Veda's IP.

4. Database Architecture — Polyglot Persistence

Recommendation Guiding principle: Right tool for the data shape. A single-database stack is wrong at this scale; a 12-database stack is operational suicide. We choose 6 databases, each with a non-negotiable use case.

Database Type Purpose in Veda Why Chosen Alternatives Considered
PostgreSQL Relational (OLTP) Users, courses, enrollments, billing, all transactional state. ACID, JSONB hybrid flexibility, mature replication, pgvector for hybrid embeddings. MySQL (weaker JSON & types); CockroachDB (overkill until truly global write).
MongoDB Document Lesson content, question banks, flexible learning materials. Schema fluidity for varied content shapes; aggregation pipeline. PostgreSQL JSONB (viable; chosen Mongo where shape varies extremely).
Redis In-memory KV Sessions, rate-limit buckets, real-time leaderboards, BKT state cache, queue backing. Sub-ms latency; rich data structures; Streams for lightweight queues. Memcached (no data structures); KeyDB (smaller community).
Qdrant Vector Embeddings for AI tutor RAG, semantic course search, content similarity. Rust core, payload filtering, on-disk indexes, mature. Weaviate, Milvus, pgvector (good for small scale).
Neo4j Graph Concept/prerequisite graph; skill graph; learning pathways. Native graph traversal; Cypher is mature; appropriate for traversal-heavy queries. ArangoDB (multi-model); Amazon Neptune (vendor-locked).
ClickHouse Columnar (OLAP) Event analytics, learning telemetry, dashboards. 10–100× faster than PG on aggregations at scale; cheap on commodity disk. BigQuery (great but vendor-locked & costs balloon); Druid (operationally heavy).

4.1 Why Not Cassandra / Elasticsearch as primary?

  • Cassandra: considered for write-heavy telemetry, but ClickHouse already handles this with better query semantics. Adding Cassandra would mean two write paths for similar data. Re-evaluate at >1B events/day.
  • Elasticsearch / OpenSearch: considered for full-text search, but PostgreSQL FTS + Qdrant hybrid search suffices for v1. Add OpenSearch when log search and complex relevance tuning become real bottlenecks. Premature adoption pays a 6-figure annual ops tax.

4.2 Per-Database Detail

PostgreSQL — System of Record

  • Tables: users, tenants, courses, enrollments, assessments, attempts, subscriptions, payments.
  • Scaling: Single primary + read replicas (1–3 initially). Move to Citus / partitioning by tenant_id once a single primary becomes hot. Logical replication to ClickHouse for analytics ingest.
  • CAP positioning: CP — we trade availability for consistency on transactional state. Correct tradeoff for billing.

MongoDB — Content Store

  • Collections: lessons, question_bank, media_metadata, interactive_widgets.
  • Scaling: Sharded by tenant_id once cluster crosses ~1 TB.
  • CAP positioning: AP-leaning (tunable consistency); content reads should never block on a primary failover.

Redis — Hot State

  • Structures used: Strings (session), Hashes (per-user feature flags), Sorted Sets (leaderboards, due-queues), Streams (lightweight pub/sub), HyperLogLog (analytics approximations).
  • Topology: Cluster mode with replicas; AOF + RDB persistence; Redis is not a database of record, only cache/state.

Qdrant — Vector Index

  • Indexes per tenant to prevent cross-tenant retrieval bleed.
  • HNSW for in-memory speed; product quantization for cost reduction at scale.
  • Re-embedding pipeline triggered on content updates via Argo Workflows.

Neo4j — Knowledge Graph

  • Nodes: Concept, Skill, Course, LearningObjective, Standard (e.g., Common Core, NCERT).
  • Edges: PREREQUISITE_OF, TEACHES, ASSESSES, ALIGNS_WITH.
  • Why graph DB and not PG recursive CTE? Traversals 5+ hops deep with mixed edge types — recursive CTEs become O(n²) and unmaintainable at 100k+ concepts.

ClickHouse — Analytics Warehouse

  • Tables: events_raw, events_enriched, daily_user_rollups, cohort_metrics.
  • Ingestion: Kafka → ClickHouse Kafka Engine → MaterializedView rollups.
  • Query pattern: Sub-second dashboards over billions of events.

7. AI-Powered Educational Features

7.1 Personalized Learning Engine

Inputs:

  • Knowledge state (BKT posteriors per concept)
  • Engagement signals (time-on-task, drop-off points, retry counts)
  • Stated goals (exam prep, skill acquisition, curiosity)
  • Affective signals (sentiment from tutor chats — used cautiously)

Output: an ordered queue of learning activities (study, practice, review, assess) with predicted learning gain.

Pipeline:

Signals → Feature Store (Feast) → Ranker (LightGBM + LLM rerank) → Constraints → UI

Recommendation LightGBM for the ranker, not a big neural network. Reasoning: tabular features, interpretability for teachers, fast inference. Use the LLM only to rerank top-N with pedagogical reasoning ("this student keeps making the same algebra error → schedule a remediation cluster").

7.2 AI Tutor — Design Constraints

Constraint Implementation
Curriculum-grounded RAG over institution's content; refuses out-of-scope questions for K-12.
Citation-required Every factual claim links to a source content chunk. Unsourced answers blocked by guard.
Pedagogically Socratic System prompt biases toward asking back, scaffolding, hint-laddering — not direct answers.
Age-appropriate Per-tenant content moderation profile; stricter for K-12.
Multilingual Detect input language; respond in same language unless overridden.
Bounded context Hard token budget; older turns summarized.
Refusal patterns Cannot do graded assessments for the student; will not produce answers to active exams.

7.3 Automated Assessment

Multiple-choice / short answer: deterministic; ~0 cost. Free-response: Hybrid pipeline:

  1. Rubric extraction from teacher's rubric → structured criteria.
  2. LLM grading against rubric, producing per-criterion score + justification.
  3. Confidence threshold: below threshold → human-in-the-loop teacher review.
  4. Bias audit: weekly statistical comparison of LLM grades vs teacher grades by demographic; flag drift.

Recommendation Critical: LLM grades are never final without teacher acceptance for high-stakes assessments. Marketing claim is "grade 80% faster", not "grade autonomously".

7.4 Speech-to-Text Learning

  • Pronunciation feedback (language learning): Whisper + alignment + scoring. On-device tiny model for offline.
  • Lecture transcription: server-side Whisper-large; chunked timestamps.
  • Voice-driven tutor for accessibility (visual impairment, low-literacy parents).

7.5 Multilingual Education

  • Content authoring once, served many. Authoring UI allows teacher to mark canonical language; translation to target locales via NMT (NLLB-200 or vendor) with teacher review queue before publish.
  • Translation memory at the segment level — paid edits propagate.
  • Right-to-left support mandatory (Arabic, Hebrew, Urdu).

7.6 Adaptive Testing (CAT)

Computerized Adaptive Testing using 2PL IRT model:

  • After each item, update ability estimate θ.
  • Select next item to maximize Fisher information at current θ.
  • Stop when SE(θ) < threshold or item budget hit.

Result: ~50% fewer items for same measurement precision vs fixed-form tests.

9. Security Architecture

9.1 Zero-Trust Foundation

Principle Implementation
Never trust, always verify Every request — inter-service included — carries JWT + mTLS.
Least privilege RBAC + ABAC; default-deny; reviewed quarterly.
Assume breach Honeytokens, behavioral anomaly detection, isolated blast radius per tenant.
Continuous verification Short-lived tokens (15 min access, 7 day refresh w/ rotation).

9.2 Identity & Access

  • End users: OAuth2 / OIDC via Ory Hydra + Kratos.
  • Workforce: Okta / Google Workspace SSO + SCIM provisioning.
  • Service-to-service: SPIFFE/SPIRE workload identities; mTLS enforced by Envoy/Istio.
  • Break-glass admin: hardware key (YubiKey) required; all sessions recorded.

9.3 Encryption

Data State Mechanism
In transit (external) TLS 1.3, HSTS, perfect forward secrecy.
In transit (internal) mTLS via service mesh.
At rest (DB) AES-256 disk + column-level encryption for PII.
At rest (S3) SSE-KMS with per-tenant keys for enterprise tier.
Backups Encrypted; restores tested.
Secrets Vault / AWS Secrets Manager; never in code, never in env vars in images.

9.4 Application Security

  • OWASP Top 10 coverage as a baseline, not a goal.
  • SAST (Semgrep), DAST (ZAP) and SCA (Dependabot, Snyk) gating CI.
  • WAF at edge (CloudFront + AWS WAF or Cloudflare).
  • Rate limiting per IP, per user, per tenant — three layers.
  • Input validation at gateway (Pydantic / Zod schemas).

Key moments of truth:

  • First 5 minutes: must reach "learning a thing" — no admin friction.
  • First assessment: must feel fair, not punitive; show progress, not just score.
  • First struggle: tutor + scaffolded hints; never a dead end.

13.2 Teacher Journey

Class setup ─► Curriculum import / map to graph ─► Roster sync ─► Assign work ─► Monitor dashboards ─► Intervene ─► Grade (AI-assisted) ─► Iterate

Anti-pattern to avoid: dumping AI grades on teachers without explanation. Each AI suggestion must show why and let the teacher overrule with one click.

13.3 Admin Workflow

  • Tenant setup (SSO, branding, data residency choice).
  • Roster / SIS integration (OneRoster).
  • License management; seat reclamation.
  • Compliance reports (FERPA/GDPR DSAR fulfillment).
  • Outcome dashboards: equity gap, mastery distribution, at-risk cohorts.

13.4 Parent Dashboard

  • Plain-language summary: "This week, Aarav mastered 4 concepts in fractions and is stuck on common denominators."
  • Concrete next step: 1–2 things they can do at home, reading-level appropriate.
  • No raw data dumps. Parents bounce off PDF gradebooks; invest in narrative + 2 charts.
  • Localized for parent literacy: text + voice playback; SMS digest for low-bandwidth households.

13.5 Accessibility

  • WCAG 2.2 AA as a launch gate, not a backlog item.
  • Screen reader tested with NVDA + VoiceOver each release.
  • Keyboard-only navigation paths covered in e2e tests.
  • Captions mandatory on all instructional video; auto-generated then teacher-corrected.
  • Color contrast and dyslexia-friendly font option.
  • Low-bandwidth mode (text-only fallback) for 2G/3G users.

14.2 Most Cost-Efficient Architecture

  1. Self-host LLM inference for sustained workloads on GPU spot pools — typically 60–80% cheaper than API per token at steady volume.
  2. Aggressive CDN + edge cache — content-heavy products live or die on cache-hit ratio; target ≥95%.
  3. Spot + reserved + on-demand mix at ~70/20/10 across stateless tiers.
  4. Single primary cloud, portable substrate — multi-cloud reality where it pays (AI), not as a religion.
  5. Right-size databases by workload rather than running everything as managed Aurora.

14.3 Most Scalable Approach

  • Stateless service tier sized by HPA + KEDA event metrics, not just CPU.
  • Event-sourced telemetry — replayable, partitioned by tenant.
  • Per-tenant resource quotas in Kubernetes; one greedy tenant cannot starve another.
  • Sharding strategy chosen now, executed later — tenant_id is a column on every relevant table from day 1.

14.4 Highest-ROI Strategic Bets

  1. Knowledge graph as core abstraction. Every dollar spent here compounds — recommendations, search, content reuse, analytics, and certification all lever off it.
  2. AI tutor with verifiable citations. The market is saturated with chatbots; trustworthy tutors are not.
  3. Emerging-markets mobile-first. Where the demand is growing fastest and incumbents are weakest.
  4. Institutional B2B as primary channel. Better LTV:CAC than B2C; structural moat through integrations.
  5. Open data export & LTI compliance. Counter-intuitive but a sales accelerator — it removes the "what if we want to leave" objection.

  • Open standards over proprietary — LTI 1.3, xAPI, OneRoster, IMS Caliper — the slow-moving but compounding bets.
  • Schema evolution discipline — Protobuf with required compatibility, no breaking changes without dual-write windows.
